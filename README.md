# SmartQuarter — Умный Квартал

Мини-приложение в MAX для жителей и председателей многоквартирных домов.
Житель сообщает о проблеме с фотографией, соседи подтверждают её, председатель
готовит заявление и ведёт статус решения. Объявления, опросы, календарь,
инициативы и справочник служб доступны участникам своего дома.

- **Вход в MAX:** https://max.ru/t365_hakaton_max_bot — запустить бота и открыть мини-приложение.
- **Приложение и API:** https://maxhack.ru; API — `/api/v1`.
- **Готовность:** https://maxhack.ru/api/v1/health → `200 {"status":"ready"}`.
- **Исходники:** https://github.com/ZheglY/SmartQuarter.
- **Инструкция проверяющему:** [доступ, роли и сценарии](docs/submission/reviewer-guide.md).
- **Контракты:** [OpenAPI 3.1](contracts/openapi/openapi.yaml), [DATA-API 1.0](DATA-API.yaml).

## Фиксация версии для сдачи

Перед отправкой материалов зафиксируйте итоговый коммит командой `git rev-parse HEAD`
и укажите его в техническом слайде вместе со ссылкой на репозиторий. Проверяющий
может выполнить `git checkout <переданный-SHA>`. Не используйте название ветки или
число коммитов вместо хеша. После дедлайна сдаваемая версия остаётся неизменной.

## Основной сценарий и роли

1. Пользователь открывает Mini App из бота MAX. Приложение проверяет подписанный
   `initData`; браузер без MAX не предоставляет вход в рабочий аккаунт.
2. Житель находит дом или вводит приглашение и отправляет заявку. Председатель принимает
   её, после чего житель выбирает дом. До принятия данные дома недоступны.
3. Житель создаёт заявку с JPEG/PNG, категорией, описанием и местом. Фото сохраняется
   в S3, заявка появляется у участников дома.
4. Другой житель подтверждает заявку один раз. Повторное подтверждение отклоняется.
5. Председатель формирует черновик заявления, проверяет текст и самостоятельно отправляет
   его адресату. Изменения статуса отражаются в карточке и истории.
6. В «Сообществе» жители голосуют, просматривают события, предлагают и поддерживают
   инициативы. Председатель публикует объявления, создаёт опросы и события.

| Роль | Права |
|---|---|
| Житель | Вступление; в принятом доме — проблемы, подтверждения, новости, голосование, календарь, инициативы и поддержка |
| Председатель дома | Заявки жильцов, приглашения, контакты, заявления, статусы проблем, объявления, опросы и календарь |
| Администратор платформы | Одобрение регистрации домов, разрешение регистрации, назначение и снятие председателя конкретного дома |

Админка: **Профиль → Администрирование платформы**. Разрешение регистрировать новые
дома не даёт управление существующим домом. Для этого администратор назначает
пользователя именно в карточке дома. У дома один председатель; замена переводит
предыдущего в жители этого дома. [Подробные правила](docs/product-workflows.md).

## Архитектура и данные

MAX → React Mini App → HTTPS/Caddy → Go Gateway → Identity / Issue / Community (gRPC).
У каждого доменного сервиса своя PostgreSQL. Redis хранит сессии, ограничения запросов,
ключи идемпотентности и поток событий. Transactional outbox связывает изменения БД
с уведомлениями. Фотографии загружаются напрямую в закрытый S3 по подписанным URL.

| Компонент | Назначение | Порт внутри Docker |
|---|---|---|
| Caddy | HTTPS, frontend и проксирование `/api` | 80, 443 TCP; 443 UDP |
| Mini App | React, TypeScript, MAX Bridge | 8080 HTTP |
| max-gateway | Проверка MAX, сессии, API, права, webhook, уведомления | 8080 HTTP |
| identity-service | Пользователи, дома, роли, вступление и регистрация | 50051 gRPC, 8081 HTTP |
| issue-service | Фото, заявки, подтверждения, заявления, история | 8082 gRPC, 8083 HTTP |
| community-service | Объявления, опросы, события, инициативы, контакты | 9090 gRPC, 8084 HTTP |
| PostgreSQL × 3 | Раздельные данные сервисов | 5432 в каждом контейнере |
| Redis | Сессии, rate limit, идемпотентность, Streams | 6379 |

На сервере публикуются только 80/443. Базы, gRPC и Redis доступны внутри Compose-сети.
Пользователь определяется проверенными данными MAX, дом — серверной сессией, права —
действующим membership. Роль из браузера не принимается. Фото доступны по временным
ссылкам; постоянного публичного чтения bucket нет. Демонстрационные примеры
не являются реальными обращениями или подтверждёнными происшествиями.

## Воспроизводимый запуск в Docker

Рабочий рецепт: **deploy/server/compose.yaml**. `deploy/docker-compose.yml` — старый
каркас и для сдачи не используется. Нужны Docker Engine и Compose v2; целевой сервер —
Ubuntu 24.04 LTS. Go и Node на хосте для Docker-сборки не требуются.

Перед первым запуском:

1. Скопируйте `deploy/server/.env.example` в `deploy/server/.env` и заполните таблицу ниже.
2. Настройте домен/DNS на сервер и доступ к портам 80/443.
3. Создайте бота MAX, привяжите HTTPS-адрес Mini App и настройте webhook
   `https://<APP_DOMAIN>/webhooks/max` с тем же `MAX_WEBHOOK_SECRET`.
4. Подготовьте приватный S3 bucket, ключи и CORS для домена приложения.
5. Подготовьте доверенный CA-bundle хоста для HTTPS-запросов к MAX. Инструкция и
   официальный источник сертификатов приведены в [руководстве](docs/deployment/server-guide.md).

**Одна команда из корня репозитория запускает все компоненты приложения:**

```bash
docker compose --env-file deploy/server/.env -f deploy/server/compose.yaml up -d --build
```

Identity применяет встроенные миграции при старте. `issue-migrate` и `community-migrate`
выполняются перед запуском зависимых сервисов. Обычный запуск сохраняет существующие
Docker volumes. Команда не регистрирует внешнего бота и не создаёт облачный bucket.

Проверить состояние:

```bash
docker compose --env-file deploy/server/.env -f deploy/server/compose.yaml ps
curl --fail https://<APP_DOMAIN>/api/v1/health
```

Остановить и снова запустить без удаления данных:

```bash
docker compose --env-file deploy/server/.env -f deploy/server/compose.yaml stop
docker compose --env-file deploy/server/.env -f deploy/server/compose.yaml up -d
```

Для production не используйте `down -v`: этот флаг удаляет данные volumes.
Перед обновлением сделайте резервную копию. [Обновление, откат и backup](docs/deployment/server-guide.md).

### Окружение и внешние зависимости

| Переменная в `deploy/server/.env` | Назначение |
|---|---|
| `APP_DOMAIN`, `ACME_EMAIL` | Домен без `https://` и адрес для HTTPS-сертификата |
| `IDENTITY_DB_PASSWORD`, `ISSUE_DB_PASSWORD`, `COMMUNITY_DB_PASSWORD` | Три разных пароля БД; случайные hex-строки не требуют URI escaping |
| `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME` | Токен и имя своего бота MAX |
| `MAX_WEBHOOK_SECRET` | Секрет, совпадающий с настройкой webhook у MAX |
| `MAX_CA_BUNDLE` | Путь к CA-bundle на Linux-хосте; по умолчанию `/etc/ssl/certs/ca-certificates.crt` |
| `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT` | Endpoint S3 и адрес, доступный браузеру по HTTPS |
| `S3_REGION`, `S3_BUCKET` | Регион и имя приватного bucket |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Ключи сервисного аккаунта с доступом к этому bucket |
| `ADMIN_USER_IDS` | Внутренние UUID администраторов через запятую; это не числовые MAX ID |

MAX нужен для настоящего входа, запуска Mini App и уведомлений; облачный S3 — для фото.
Они не воспроизводятся production Compose. Доступ к ним необходим на весь период
проверки. Для автономных тестов предусмотрены MinIO и тестовый получатель сообщений MAX.
На свежем развёртывании администратор сначала входит через MAX; оператор определяет
его UUID по [инструкции](docs/deployment/server-guide.md) и указывает `ADMIN_USER_IDS`.
Дальнейшие назначения выполняются через UI.

Рабочие токены и `.env` не входят в репозиторий. Передавайте доступ организаторам
отдельным защищённым способом. `docker compose config --quiet` проверяет конфигурацию,
не печатая значения секретов.

## Проверка и тестовые данные

### Автоматическая приёмка без настройки аккаунтов и облака

Из корня репозитория:

```bash
docker compose -f deploy/test/compose.yaml run --build --rm test
```

Это отдельный проект `smartquarter-acceptance`: реальные сервисы, PostgreSQL, Redis,
MinIO и синтетические пользователи только в тестовой БД. Порты не публикуются, настоящие
MAX и production БД не используются. Стенд сам создаёт пользователей, дома и данные,
проверяет роли и основной workflow, затем выполняет все 48 проверок из `DATA-API.yaml`,
включая внешний PUT/GET фотографии в MinIO.

Ожидаются `PASS` для интеграционных тестов и `PASS: 48 API checks and external S3 upload/download`.
Сбросить только этот тестовый стенд перед повторным чистым прогоном:

```bash
docker compose -f deploy/test/compose.yaml down -v
```

### Проверка через настоящий MAX

[Инструкция для жюри](docs/submission/reviewer-guide.md) описывает вход, текущий дом
«ПИК», приём заявки, выделенный дом для проверки председателя и пошаговые действия
с ожидаемыми результатами. Здесь нужны реальные пользователи MAX; тестовый вход
с выдуманной ролью в production не предусмотрен.

После однократной подготовки отдельного тестового дома исполнитель
[run_checks.py](tools/data-api/README.md) создаёт проверочные записи через API без
SQL, ручного наполнения БД и изменения пользователей/ролей. Нужны три разных
участника: автор, сосед и председатель. Действующие cookie передаются закрыто и не
записываются в YAML. По умолчанию исполнитель лишь показывает план; запись включается
явным `--execute` и требует UUID выбранного дома.

Данные запросов находятся в [DATA-API.yaml](DATA-API.yaml), фотография —
[stair-light.png](scripts/demo-content/images/stair-light.png). Новые записи отмечены
`[DATA-API]`. Временное событие удаляется, опрос и инициатива закрываются. Заявка,
заявление и объявление остаются как история проверки: API их удаления не предоставляет.
Для полной очистки используйте сброс отдельного локального тестового стенда.
[Скрипт замены демонстрационного контента](scripts/demo-content/README.md)
предназначен для оператора с backup, а не для запуска жюри на рабочем доме.

### Контракты, зависимости и CI

```bash
python -m pip install -r tools/data-api/requirements.txt
python tools/data-api/validate_data_api.py DATA-API.yaml --openapi contracts/openapi/openapi.yaml
python -m unittest discover -s tools/data-api -p "test_*.py"
```

Валидатор организаторов проверяет структуру, ссылки и пути OpenAPI; сам HTTP-запросы
не отправляет. [Исполнитель и особенности S3](tools/data-api/README.md).

Сервисы используют Go 1.26.x (`services/*/go.mod` и `go.sum`); frontend — Node 24
(`web/miniapp/package.json` и `package-lock.json`). У Python-инструментов отдельный
`tools/data-api/requirements.txt`. CI проверяет Go, protobuf, OpenAPI, DATA-API,
типизацию/lint frontend, модульные и браузерные тесты, Docker-сборки и общий workflow.
Автоматический production deployment не настроен.

## Известные ограничения

- Заявления отправляет председатель самостоятельно. Нативное скачивание `.txt`
  в MAX ограничено; предусмотрено копирование текста.
- У дома один председатель. Регистрация и вступление требуют одобрения;
  автоматического присвоения прав проверяющему нет.
- Сессия MAX по умолчанию действует 12 часов. Для последующей проверки нужно заново
  открыть Mini App и получить свежую сессию; токен бота не является пользовательским входом.
- DATA-API 1.0 не описывает бинарный обмен с отдельным S3 endpoint.
  Наш исполнитель выполняет этот шаг; при другом исполнителе нужно согласовать
  внешний PUT перед `photo-complete`. В YAML это явно указано.
- Демонстрационные фотографии — вымышленные иллюстрации, контакты примеров нерабочие.
- Docker-тесты не заменяют проверку входа, уведомлений, клавиатуры, кнопки «Назад»
  и копирования на настоящих клиентах MAX Android/iOS.
- Сборку до пяти минут нужно замерить на машине приёмки отдельно, исключая загрузку
  базовых образов. Скорость зависит от CPU и доступа к реестрам;
  факт зелёного CI сам по себе этот лимит не подтверждает.
