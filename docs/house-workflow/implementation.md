# Реализация и результаты проверок

Ветка: `feat/house-identity-service`. База: `cc8c0d7`.
Исторический отчёт о первоначальном workflow. Последующее расширение: [роли и сообщество](../product-workflows.md).
Проверки выполнены локально 23 сентября 2026 года.

## Реализовано

- Identity: модерация регистрации домов, поиск, заявки жильцов, приглашения,
  управление участниками, передача председательства, настройки уведомлений.
- PostgreSQL: миграция, уникальность нормализованного адреса и действующего
  председателя, транзакционные аудит и outbox, конкурентные переходы состояний.
- Gateway: типизированные REST/gRPC-контракты, проверка актуальных прав до
  повторения идемпотентного ответа, доставка событий через Redis с повторами и DLQ.
- Community: справочник служб дома, проверка данных, архивирование, аудит и события.
- Mini App: регистрация и вступление без предварительного членства, экраны
  модератора/председателя/жителя, приглашения, передача роли, контакты и настройки.
- MAX: меню и ссылки запуска нужных экранов; уведомления учитывают текущий доступ
  и пользовательские настройки. Внешняя доставка в автотестах заменяется HTTP-стендом.
- Compose и CI: миграции, конфигурация администратора платформы, проверки контрактов,
  интеграционные тесты с PostgreSQL и общий приёмочный workflow.

Приёмочный стенд использует реальные PostgreSQL, Redis, S3-совместимое хранилище
и внутренние сервисы. Проверены также отказ бывшему председателю, изоляция домов,
повтор приглашения, отмена/отклонение заявок, настройки и дедупликация уведомлений.
После последней правки счётчика входящих заявок повторены тесты Identity
с реальной PostgreSQL, `go vet` для затронутых пакетов и общий Docker workflow.
Повторный запуск на использованной базе выявил зависимости тестов от старых
участников и от момента фиксации outbox: теперь каждый House-прогон создаёт новых
пользователей, а Issue-проверка ожидает фиксацию публикации с ограниченным таймаутом.

GitHub Actions не запускался удалённо в рамках этой проверки: изменения ещё не
отправлены. Проверка настоящих MAX-аккаунтов, домена и HTTPS выполняется после
развёртывания по [руководству](README.md#max-ручная-проверка-после-деплоя).

## Эксплуатационные границы

Администраторы платформы задаются только через `ADMIN_USER_IDS`; роль дома `ADMIN`
не заменяет этот список. Приглашение требует одобрения председателем. Адресная
дедупликация не подтверждает право собственности. Уведомления имеют семантику
at-least-once; редкий повтор после сбоя между MAX Send и записью результата возможен.

Лимиты списков, общий транзакционный advisory lock, отложенные расширенные диалоги
бота и экраны опросов/календаря описаны в [руководстве](README.md). Нагрузочная
проверка и реальный деплой не выполнялись. Docker, Go-кэши и рабочие временные
каталоги для сборок размещены на D:.
