# DATA-API: описание и выполнение проверок

`validate_data_api.py` и `DATA-API.schema.json` — неизменённые по содержимому файлы
[организаторов](https://gitverse.ru/stasnorman/example-data-api), commit
`8504a6d9b39e6f652bce689d96e88538d7541c6b` (повторно сверено 29.09.2026).
Автор — Станислав Макиевский; условия сохранены в `UPSTREAM-LICENSE.md`.
`run_checks.py` — отдельный исполнитель нашего проекта, а не часть стандарта организаторов.

## Проверка формата

```bash
python -m pip install -r tools/data-api/requirements.txt
python tools/data-api/validate_data_api.py DATA-API.yaml --openapi contracts/openapi/openapi.yaml
python -m unittest discover -s tools/data-api -p "test_*.py"
```

Код 0 валидатора означает правильную структуру, ссылки и совпадение методов/путей
с OpenAPI. Валидатор HTTP-запросы не выполняет. В YAML 48 проверок: готовность,
сессии/права, фото, создание заявки, подтверждение другим жителем, заявление,
все последовательные статусы до решения, объявления, голосование, календарь,
инициативы, контакты и чтение настроек уведомлений.

Административное назначение и снятие ролей проверяются отдельным интеграционным
workflow и вручную по [инструкции](../../docs/submission/reviewer-guide.md).
DATA-API не меняет действующие роли, пользователей или дома.

## Обязательный внешний шаг фотографии

Gateway выдаёт `presigned_url` и `required_headers` в `photo-upload`. Сам файл
`scripts/demo-content/images/stair-light.png` (2 093 740 байт) отправляется **PUT в S3**,
а не в Gateway. Затем выполняется `photo-complete`.

DATA-API 1.0 задаёт один `api.baseUrl` и относительные пути; в нём нет стандартного
поля для бинарного файла и другого origin. Поэтому мы не добавляли выдуманные
поля в схему и не описывали несуществующий proxy endpoint. В `description`
загрузки явно указан внешний шаг. Наш исполнитель делает PUT автоматически,
а после `photo-download` скачивает файл и сравнивает байты. При использовании
иного исполнителя нужно согласовать с организаторами такой hook или остановку
между `photo-upload` и `photo-complete`. Один YAML без этого шага не выполнит цепочку фото.

Даты опроса/календаря фиксированы в июне 2030 года для воспроизводимой проверки 2026 года.
Перед июнем 2030 нужно обновить срок опроса: создание опроса с прошедшим сроком запрещено.
При замене фотографии обновите `size_bytes`; исполнитель проверяет размер до записи.

## Полная автономная проверка

```bash
docker compose -f deploy/test/compose.yaml run --build --rm test
```

Тестовый Gateway использует реальные сервисы и БД, а MAX заменён тестовым получателем.
Изолированный стенд сам создаёт три аккаунта и дом, передаёт их временные сессии
исполнителю через stdin и выполняет YAML плюс S3-шаги. Никаких ключей production
или настроек вручную не нужно. После проверки сбросить только тестовый проект:

```bash
docker compose -f deploy/test/compose.yaml down -v
```

## Выполнение на HTTPS-стенде с реальными сессиями

Один раз подготовьте **отдельный тестовый дом** и три разных аккаунта MAX:

| Ключ в приватном JSON | Роль в активном доме |
|---|---|
| `resident` | RESIDENT, автор заявки |
| `neighbor` | RESIDENT, сосед для подтверждения и поддержки |
| `chairman` | CHAIRMAN именно этого дома |

Все трое должны выбрать один и тот же дом. Смена ролей или активного дома не входит
в исполнитель: он проверяет их до начала и перед каждым изменяющим запросом.
Не используйте рабочий дом «ПИК» для автоматического наполнения.

Получение cookie без токена бота:

1. Войти реальным пользователем в MAX Web и открыть Mini App бота.
2. В инструментах разработчика браузера выбрать контекст `https://maxhack.ru`:
   Application/Storage → Cookies → значение `sq_session`. Если встроенный клиент
   не предоставляет devtools, использовать MAX Web в обычном браузере либо согласовать
   с командой выдачу сессии после настоящего входа. `document.cookie` не подходит:
   cookie имеет HttpOnly.
3. Для другого пользователя использовать его отдельный профиль браузера/сеанс MAX,
   повторить вход и выбрать тот же тестовый дом.
4. Сохранить только значения cookie в JSON **вне репозитория**, например
   `~/.smartquarter-review/sessions.json`, и ограничить чтение (`chmod 600` на Linux).
   Структура: ключи `resident`, `neighbor`, `chairman`, значения — соответствующие cookie
   без префикса `sq_session=`. Не пересылать файл в публичные чаты или Git.

UUID дома можно получить в ответе `GET /api/v1/me`, поле `active_house_id`, через Network
в том же браузере. При работе сессии API не требует токена бота или облачных ключей.
Сессия живёт по умолчанию 12 часов; при 401 нужно заново открыть Mini App и обновить cookie.

Посмотреть план, без сетевых запросов и изменений:

```bash
python tools/data-api/run_checks.py
```

Создать и проверить записи в заранее выбранном тестовом доме:

```bash
python tools/data-api/run_checks.py --execute \
  --house UUID_ТЕСТОВОГО_ДОМА \
  --sessions ~/.smartquarter-review/sessions.json \
  --s3-origin https://storage.yandexcloud.net
```

Для другого стенда добавить `--base-url https://review.example.com`; Origin по умолчанию
совпадает с адресом API, при необходимости задаётся `--origin`.
`--s3-origin` — точный origin адреса в подписанных ссылках, а не произвольный wildcard.
Можно повторить этот аргумент для нескольких разрешённых origins. Исполнитель
не следует перенаправлениям и не передаёт cookie приложения в S3.
HTTP разрешён только специальным флагом для loopback Gateway интеграционных тестов;
при обычном запуске TLS-проверка включена.

Ожидаемый результат: `PASS: 48 API checks and external S3 upload/download` и код 0.
На ошибке код 1, идентификатор шага и HTTP-статус; значения cookie, подписанные ссылки
и тела ответов не выводятся. Не запускайте повтор после неизвестного сетевого результата
вслепую: проверьте созданные записи. Каждый полный запуск создаёт новый набор данных.

## Что создаётся и что остаётся

Данные запросов являются открытой фикстурой в DATA-API.yaml; фото прилагается в Git.
Добавляются заявка с фото, подтверждение, заявление, объявление, опрос/голос,
событие, инициатива/поддержка. Префикс `[DATA-API]` отличает их от обычных записей.
Это не замена существующего демонстрационного контента и не сброс БД.

В `finally` выполняется `cleanup` только для ID, полученных при этом запуске:
удаляется событие, закрываются опрос и инициатива. При истекшей сессии/сбое сети
очистка может не завершиться — исполнитель сообщает об этом и возвращает ошибку.
Идентификаторы созданных объектов выводятся для сверки.

**Важное ограничение реализации:** удаления заявки, заявления, объявления,
опроса и инициативы через API нет. Закрытие не является удалением. Эти объекты
останутся историей отдельного тестового дома; скрытого DELETE/SQL-cleanup нет.
Для полностью чистого повторного прогона используйте локальный изолированный стенд.
Уведомления при создании записей на живом сервере подчиняются обычным настройкам;
исполнитель их не отключает. Отдельный дом исключает рассылку жильцам «ПИК».
