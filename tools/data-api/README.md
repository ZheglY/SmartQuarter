[репозитория организаторов](https://gitverse.ru/stasnorman/example-data-api),

Из корня проекта:

```bash
python -m pip install -r tools/data-api/requirements.txt
python tools/data-api/validate_data_api.py DATA-API.yaml --openapi contracts/openapi/openapi.yaml
```

Код 0 означает корректность структуры, связей проверок и соответствие путям OpenAPI.
Валидатор не отправляет HTTP-запросы. Проверка также включена в GitHub Actions.

## Подготовка технической проверки

1. Развернуть версию приложения с миграциями Identity 000003 и Community 000003.
2. Создать отдельный тестовый дом, назначить председателя и принять тестового жителя.
3. Получить сессии через реальный вход MAX. Роли `chairman` и `resident` должны иметь
   один активный тестовый дом; `admin` — внутренний UUID из `ADMIN_USER_IDS`.
4. Передать действующие cookie `sq_session` проверяющему по защищённому каналу.
   Исполнитель подставляет соответствующую cookie для каждой роли. Для `public`
   cookie не передаётся. Токен бота и ключи S3 для проверок не нужны.
5. Выполнить `checks` по порядку. После создания события всегда выполнить `cleanup`,
   даже если последующие шаги завершились ошибкой. Удалять только полученный `eventId`.

`DATA-API.yaml` содержит 15 проверок и удаление созданного тестового события.
Секретов и фиксированных идентификаторов пользователей в нём нет. Если адрес
развёртывания отличается, измените `api.baseUrl` и `Origin` на фактический домен.
Даты события намеренно фиксированы в 2030 году: календарь допускает исторические
и будущие события, поэтому повторная проверка не зависит от текущей даты.

Полные сценарии голосования, заявок, ролей, фотографий и уведомлений проверяются
отдельным стендом `deploy/test/compose.yaml` и браузерными тестами `web/miniapp`.
